# 应用开发流水线（app-dev-flow）

六阶段**门禁制**流水线：每个阶段产出物完成后，**停等人工确认**，确认后才进入下一阶段。禁止跳级、禁止"边开发边补文档"、禁止以代码反向定义需求。

## 触发条件

用户要求开发新应用/新功能、写 PRD/技术方案/UI 设计、或进入"开发交付"类任务时加载。

## 流水线总览

```
文档阶段 → 门禁确认 → AI 开发 → 自动测试 → 独立审查 → 记录变更
   ↑__________ 每个阶段完成才有下一阶段 __________↓
工件链: PRD → 技术方案 → UI 设计 → 代码（文档永远是单一事实来源）
```

## 六阶段与门禁（每阶段必须停等确认）

### 阶段 1：文档（文档先行，四个工件依次产出，每个工件也需门禁）

1. **PRD（产品需求文档）**：用户场景、功能清单、验收标准（Given/When/Then）、非功能需求（性能/安全/兼容）
2. **技术方案**：架构图、技术选型（含理由）、数据模型、接口设计、风险与备选方案
3. **UI 设计**：页面结构、组件清单、交互流程、状态设计（空/加载/错误/边界）
4. **开发任务清单**：将 PRD 拆解为可执行任务块（TDD 驱动，每个任务块含测试先行描述）

> **门禁 A**：以上四件文档交付后停等确认。用户确认或提出修改，修改后再确认。**未经确认禁止进入编码**。

### 阶段 2：AI 开发（按任务块执行，TDD）

- 每个任务块：先写失败测试（RED）→ 最小实现（GREEN）→ 重构（REFACTOR）
- 代码与文档逐条映射（需求编号 → 实现 → 测试）
- 遵守既有代码规范（命名、目录、依赖管理）
- git：每个任务块一个 commit，commit message 关联需求编号

### 阶段 3：自动测试

- 单元测试 → 集成测试 → 端到端测试 全量回归
- 测试报告：覆盖范围、通过率、性能数据
- 缺陷修复后重新全量回归（退化即拦截）

### 阶段 4：独立审查（代码 + 文档一致性）

- 逐条核对：PRD 每条需求 → 代码实现 → 测试用例 双向可追溯
- 检查：隐藏需求遗漏、边界处理缺失、文档与实现漂移
- 输出审查结论（通过 / 需修改清单）

### 阶段 5：记录变更

- 更新 CHANGELOG、版本号（semver）
- 归档决策记录（ADR：为什么这样设计）
- 更新跟踪表（需求状态：完成/部分/未做）

## 核心纪律

- **门禁不可跳过**：任何阶段未确认，不进入下一阶段
- **文档是唯一事实来源**：代码与文档冲突时，先改文档再改代码
- **测试不合格不算完成**：无测试报告的功能视为未交付
- **最小改动**：不擅自扩大变更范围

## Pitfalls

- 用户说"直接写代码吧"≠跳过文档门禁——至少产出最小 PRD + 技术方案并快速确认
- 不要在一个阶段里混入下一阶段的工作（如写 PRD 时就开始设计数据库表）
- 门禁确认不是摆设：确认时明确列出"已确认内容 + 未决问题"，防止模糊确认

## 验证

- 每个阶段交付物可独立审计（PRD 有版本、技术方案有评审、测试有报告）
- 需求-代码-测试三方追溯矩阵完整
