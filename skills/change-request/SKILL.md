# 需求变更流程（change-request）

五步标准流程处理需求变更。**核心铁律：文档永远是单一事实来源**——任何变更先落到文档，代码/测试/跟踪表全部以文档为准，禁止"口头变更直接改代码"。

## 触发条件

用户提出新需求、修改既有需求、调整范围、或发现"需求与实现不一致"时加载。

## 五步流程（每步有产出物）

### 1. 变更提出（Change Request）
- 记录变更内容：**谁**在**何时**提出，变更**什么**，**为什么**
- 区分变更类型：新功能 / 修改行为 / 删除功能 / 修 bug / 非功能调整

### 2. 影响评估（Impact Assessment）
逐维度评估并输出书面结论：
- **文档影响**：PRD / 技术方案 / UI 设计 哪些章节需更新
- **代码影响**：涉及模块、接口、数据模型
- **测试影响**：需新增/修改的测试用例
- **依赖影响**：上游/下游依赖、第三方服务
- **成本影响**：工作量、时间、风险
- 结论三选一：**接受 / 拒绝（附理由）/ 需澄清**

### 3. 更新文档（先文档后代码，不可逆顺序）
- 按影响评估结果更新对应文档（PRD → 技术方案 → UI 设计）
- 文档中标注变更标记（如 `[CR-001]`），保留变更前描述或变更历史
- **门禁**：更新后的文档经用户确认后，才进入任务块生成

### 4. 生成任务块（Task Breakdown）
- 将变更拆解为可执行任务块，每个任务块包含：目标、涉及文件、验收标准、关联文档编号
- 任务块按依赖排序，标注哪些是新增、哪些是修改
- 与既有任务合并/冲突时，明确处置（替换/并存）

### 5. 更新跟踪表（Traceability）
- 变更跟踪表：CR 编号 | 提出时间 | 类型 | 状态 | 关联文档版本 | 任务块 | 完成时间
- 需求-文档-代码-测试四方追溯矩阵同步更新
- 全流程状态流转：提出 → 评估中 → 已确认 → 实施中 → 已验收 → 已关闭

## 核心纪律

- **文档永远是单一事实来源**：先改文档 → 确认 → 再改代码 → 最后同步跟踪表
- **禁止**：直接改代码再回头补文档；口头确认不落文档；变更不评估影响就动手
- **每份文档标注变更来源**（CR 编号），保证可追溯
- 变更积累多个时，按 CR 编号分别跟踪，不混为一谈

## Pitfalls

- 用户说"小改一下"——仍走完整流程（评估可以很轻量，但不可省略）
- 变更导致文档与已交付功能冲突时，以**最新确认的文档**为准并显式通知受影响方
- 不要用"更新跟踪表"代替"更新文档"——跟踪表是索引，文档是事实本身

## 验证

- 每条变更都能回答：CR 是什么、影响哪些文档、改了什么代码、测试是否覆盖、跟踪表是否更新
- 文档中找不到的变更 = 不存在（未落文档的变更一律不实施）
