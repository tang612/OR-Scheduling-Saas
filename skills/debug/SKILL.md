# 系统化调试（debug）

四阶段调试流程：**理解问题 → 定位根因 → 修复 → 验证**。核心纪律：**先分析再改，禁止边改边试探**；**git 是生命线，每一步一个 commit**（可回滚、可追溯、可二分）。

## 触发条件

任务涉及 bug 修复、错误排查、行为异常、测试失败定位时加载。

## 四阶段（每阶段有产出物，未完成不进入下一阶段）

### 阶段 1：理解问题（先复现，再动手）

1. **复现**：稳定复现 bug（复现步骤写成文档；无法复现 = 信息不足，先收集）
2. **收集证据**：错误信息原文、堆栈、日志、输入数据、环境（版本/OS/依赖）
3. **界定范围**：什么场景触发、什么场景不触发（隔离变量）
4. **产出**：问题描述单（现象 + 复现步骤 + 期望行为 + 实际行为）
5. **git**：确认工作区干净（`git status`），必要时先 commit 当前状态再开始

### 阶段 2：定位根因（假设驱动，禁止瞎试）

1. **提出假设**：基于证据列出 2~3 个候选根因（不猜测就动手 = 边改边试探）
2. **验证假设**：用最小实验验证（打印、单测、二分注释、git bisect），一次只验证一个假设
3. **定位到行**：根因必须定位到具体代码行/配置项/数据流，而非"大概这块"
4. **记录**：根因说明（为什么导致该现象，因果链完整）
5. **git**：定位过程的关键实验改动单独 commit（如 `debug: instrument bisect step`），方便回滚

### 阶段 3：修复（最小改动）

1. **最小修复**：只改与根因直接相关的代码，不顺手重构、不扩大范围
2. **防回归思考**：修复是否影响其他调用方？是否需要补边界测试？
3. **git**：修复单独一个 commit（`fix: <根因摘要> (closes #issue)`），与实验改动分离

### 阶段 4：验证（证明修好了）

1. **复现原 bug**：用阶段 1 的复现步骤验证不再触发
2. **回归测试**：跑相关测试套件全量（单元/集成/端到端），确认无退化
3. **边界验证**：验证相邻场景（参数边界、空值、并发）未受影响
4. **产出**：验证报告（修复前 vs 修复后行为对比）
5. **git**：验证通过后打 tag 或合并，更新 CHANGELOG

## 核心纪律

- **禁止边改边试探**：没有假设和证据之前，禁止改代码碰运气
- **禁止一次改多处**：无法区分哪个改动生效 = 无效调试
- **git 是生命线**：理解/定位/修复/验证每步都有 commit，任何一步可回滚；`git bisect` 是定位利器
- **修完必须验证**：不验证的修复 = 未完成
- **诚实声明**：根因未定时明确说"未定位"，不编造修复理由

## Pitfalls

- 跳过阶段 1 直接改代码 → 大概率修错地方或引入新 bug
- 修复与实验改动混在一个 commit → 无法回滚单项
- 用"重新安装/重启"当修复 → 治标不治本，必须找到根因
- 验证只测 happy path → 必须回归原 bug 场景 + 边界

## 验证

- 每个 bug 都能回答：现象是什么、根因在哪一行、改了什么、怎么证明修好、git 历史可回滚到哪一步
- 调试过程的 commit 链完整：`debug:` / `fix:` / `test:` 分离
